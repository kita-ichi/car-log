## 3. 層の責務

| 層 | 責務 | してはいけないこと |
|---|---|---|
| `types/` | エンティティの型定義のみ | ロジックを持たない |
| `logic/` | 燃費計算・統計・バリデーション(**純粋関数**) | UI・DB(Dexie)への依存 |
| `db/repositories/` | CRUD、燃費キャッシュの整合性維持、金額の正規化 | 画面固有の整形(表示用フォーマットはUI側) |
| UI(未実装) | 画面・状態管理。リポジトリと logic を呼ぶだけ | 燃費計算や検証ルールの重複実装 |

### 設計上の重要ポイント

1. **燃費キャッシュ(`FuelRecord.fuelEconomy`)はリポジトリ層が自動維持する。**
   `fuelRecordRepository` の create / update / remove を使う限り、
   追加・編集・削除・満タンフラグ変更時の影響区間の再計算は自動で行われる。
   **UI側で燃費を計算して保存する必要はない(してはいけない)。**
2. **金額(総額・単価)の正規化もリポジトリ層が行う。**
   総額を渡せば単価を自動算出、単価を渡せば総額を逆算、両方省略なら両方 null。
3. **日付は文字列で統一**: 日付 `'YYYY-MM-DD'`、年月 `'YYYY-MM'`、日時 ISO 8601。
   文字列比較 = 時系列比較が成立する。Date オブジェクトはDBに入れない。
4. **車両の削除は無い。** `archive()` で非表示(記録は保持)。一覧は `listActive()` を使う。
5. **愛車の写真(F-22)の画像本体は車両レコードと別テーブル。**
   車両一覧は画面表示のたびに全車両行を読むため、そこに数百KBの画像を同居させると
   写真を出さない画面(ホーム・記録入力の車両参照など)でも毎回全画像を読むことになる。
   `Vehicle` が持つのは `photoUpdatedAt`(写真の有無 + 更新時刻)だけで、
   画像は表示する側が `getPhoto()` / `getPhotos()` を呼んだときだけ読む。
   保存形式は **Blob(バイナリのまま)**。base64 はサイズが約1.33倍になるうえ
   `<img>` 表示のたびに文字列を持ち回ることになるため、DBには入れない
   (base64 にするのは JSONバックアップに書き出すときだけ)。

## 4. DBスキーマとマイグレーション

`app/src/db/database.ts` の `AppDatabase`。DB名 `car-maintenance-db`。

```
v1 (2026-07-03):
  vehicles:            id
  fuelRecords:         id, vehicleId, [vehicleId+date]
  maintenanceRecords:  id, vehicleId, [vehicleId+date], [vehicleId+type]
  settings:            key   (キーバリュー。selectedVehicleId など)

v2 (2026-07-05): 愛車の写真(F-22)
  vehiclePhotos:       vehicleId   (車両と1:1。画像本体は Blob で保持)
```

v2 は**新規テーブルの追加のみ**(既存テーブルの定義は v1 から引き継がれる)。データ変換が不要なので `upgrade()` は書いていない。既存ユーザーのデータは無変更のまま v2 に上がる。
`Vehicle.photoUpdatedAt` は非インデックスのフィールドなので、こちらはスキーマ変更が不要(既存の車両レコードはキー自体が無い = 写真なし として扱われる)。

**写真の表示調整(F-22b / 2026-08-28)もスキーマ変更なし**。`Vehicle.photoAdjust` は非インデックスのフィールドで `stores()` の定義が変わらないため、version を上げても空のアップグレードが走るだけで意味がない。既存レコードはキーを持たないままでよく、読み出し側の `normalizePhotoAdjust()` が既定値(cover + center)として扱うのでデータ変換も不要 —— **設定済みユーザーの写真の見え方は変わらない**。インデックスが必要になった時点で `version(3)` を追記する。

**スキーマ変更の手順**: 既存の `version(N)` は消さず、`this.version(N+1).stores({...}).upgrade(tx => {...})` を**追記**する(Dexie が差分マイグレーションを実行)。変更したら本メモの履歴も更新すること。

### 5.3 愛車の写真(F-22)— UI から使う手順

**保存**: 画像の縮小・圧縮はブラウザAPI(canvas)を使うため `ui/imageProcessing.ts` に薄く分離してある。

```ts
import { processVehiclePhoto } from './ui/imageProcessing'
import { vehicleRepository } from './db/repositories'
import { ImageError, formatByteSize } from './logic/image'

try {
  // File(input[type="file" accept="image/*"])を渡す。
  // 検証 → デコード(EXIFの向きを反映)→ 長辺1280pxへ縮小 → JPEG(品質0.85)
  const processed = await processVehiclePhoto(file)
  await vehicleRepository.setPhoto(vehicleId, processed) // 戻り値をそのまま渡せる
  toast(`写真を設定しました(${formatByteSize(processed.byteSize)})`)
} catch (e) {
  if (e instanceof ImageError) toast(e.message) // 日本語メッセージをそのまま表示できる
  else throw e
}
```

**表示**: 画像は Blob なので `<img src>` には ObjectURL が要る。**作った URL は必ず解放する**(解放しないとページを閉じるまでメモリに残る)。

```ts
import { createPhotoObjectUrl, revokePhotoObjectUrl } from './ui/imageProcessing'

const [url, setUrl] = useState<string | null>(null)
useEffect(() => {
  if (!vehicle.photoUpdatedAt) { setUrl(null); return }   // 一覧では読み込まない判定に使う
  let alive = true
  let created: string | null = null
  void vehicleRepository.getPhoto(vehicle.id).then((photo) => {
    if (!photo) return
    created = createPhotoObjectUrl(photo)
    if (alive) setUrl(created)
    else revokePhotoObjectUrl(created)   // アンマウント後に届いた場合
  })
  return () => { alive = false; revokePhotoObjectUrl(created) }
}, [vehicle.id, vehicle.photoUpdatedAt])   // ← photoUpdatedAt を依存に入れると差し替えで作り直される
```

**一覧のサムネイル(S-08 / S-11)**: 画面設計では行頭に44pxのサムネイルを出すため、一覧でも写真を読む必要がある。1行ずつ `getPhoto()` を呼ばず、**表示する行の分だけ `getPhotos(ids)` で一括取得**して ObjectURL をまとめて作り、アンマウント時にまとめて解放する。

```ts
const photos = await vehicleRepository.getPhotos(rows.map((v) => v.id))
const urls = new Map([...photos].map(([id, p]) => [id, createPhotoObjectUrl(p)]))
// クリーンアップ: urls.forEach(revokePhotoObjectUrl)
```

注意点:
- 写真の**有無だけ**を知りたい場面(タイプアイコンとの出し分けの判定など)では `getPhoto`/`getPhotos` は不要。`vehicle.photoUpdatedAt` で判定できる
- 保存しているのは長辺1280pxの1枚のみ(サムネイル用の縮小版は持っていない)。車両が数台のうちは44px表示でも問題ないが、登録台数が増えて一覧が重くなるようなら別途サムネイルを持たせる余地がある
- 写真の削除は `removePhoto(id)`(= `update(id, { photo: null })`)。車両は残る
- 処理後のサイズ目安: iPhone の 12MP 写真(3〜5MB)→ **150〜350KB 程度**(計算上の見積もり。実機での実測は未実施)。`processed.sourceByteSize` と `byteSize` で圧縮前後を表示できる
- **EXIF は保存データに残らない**(canvas 再エンコードのため)。向きは反映済み、撮影位置(GPS)は落ちる

### 5.3b 写真の表示調整(F-22b)— UI から使う手順

**保持する値**(`Vehicle.photoAdjust`。デザインガイド 5.15.6 と同じ定義):

| 値 | 範囲 | 既定 | 意味 |
|---|---|---|---|
| `zoom` | `MIN_PHOTO_ZOOM`(0.05)〜`MAX_PHOTO_ZOOM`(3) | **1** | **その枠を覆う最小倍率(cover)を 1 とする相対値**。1未満 = 縮小(余白が出る) |
| `focusX` / `focusY` | 0〜1 | **0.5** | **はみ出した分のどこを見せるか**(CSS `object-position` と同じ意味)。0 = 左端/上端合わせ、1 = 右端/下端合わせ |

- **既定値 `{1, 0.5, 0.5}` は `object-fit: cover` + `object-position: center` と完全に一致する**。`zoom=1` では描画サイズが必ず枠以上になり、`focus=0.5` を位置の式 `(枠長 − 描画長) × focus` に入れると `(枠長 − 描画長)/2` = 中央寄せになるため
- したがって **`photoAdjust` を持たない既存レコードは既定値として扱えばよく、表示は従来どおり**
- 倍率を枠に対する相対値で持つので、**1つの値をヒーロー(16:9)にも44pxサムネにもそのまま適用できる**

**描画のしかた**(枠は `position: relative; overflow: hidden`、`<img>` は `position: absolute`):

```tsx
import { photoFrameStyle, withMinZoom } from './logic/photoAdjust'

// 写真の実寸: img.naturalWidth/naturalHeight が最も確実。
// 保存済みの photo.width/height でもよいが、古いレコードには無いことがある
const size = { width: photo?.width, height: photo?.height }

// ヒーロー(16:9)。枠は「比」だけ渡せばよい(実ピクセルを測る必要なし)
const heroStyle = photoFrameStyle(size, { width: 16, height: 9 }, vehicle.photoAdjust)

// 44pxサムネ(1:1)。倍率だけ1以上にクランプして余白を作らせない
const thumbStyle = photoFrameStyle(size, { width: 1, height: 1 }, withMinZoom(vehicle.photoAdjust, 1))

// style が null = 実寸が分からない → 従来の cover 表示のまま(= 既定値と同じ見え方)
<img src={url} style={heroStyle ?? undefined} className={heroStyle ? 'adjusted' : ''} />
```

**重要**: 計算後のボックスは**常に写真と同じ縦横比**なので、調整値を当てる `<img>` は `object-fit: fill` にすること(`cover` のままだと二重に切り抜かれる)。CSS 側で `.adjusted { object-fit: fill }` のように出し分ける。

**調整シート(S-08 から開く全画面シート)**:

```ts
import {
  clampPhotoAdjust, containZoom, normalizePhotoAdjust,
  DEFAULT_PHOTO_ADJUST, MAX_PHOTO_ZOOM,
} from './logic/photoAdjust'

const HERO = { width: 16, height: 9 }
const [adjust, setAdjust] = useState(() => normalizePhotoAdjust(vehicle.photoAdjust))

// スライダーの範囲: 下限は「写真全体が収まる倍率」、上限は定数
const min = containZoom(size, HERO)   // 例: 縦写真 0.42 / 横4:3 0.75
const max = MAX_PHOTO_ZOOM

// プリセット
const showWhole = () => setAdjust({ zoom: min, focusX: 0.5, focusY: 0.5 })
const fillFrame = () => setAdjust({ ...DEFAULT_PHOTO_ADJUST })

// ドラッグ: Δfocus = −Δpx ÷ (描画長 − 枠長)。はみ出している軸だけ動く
//   layout.widthRatio > 1 なら横に動かせる(= photoLayout の hasGapX が false)

// 保存(範囲外の途中値は clampPhotoAdjust が丸める)
await vehicleRepository.setPhotoAdjust(vehicle.id, clampPhotoAdjust(adjust))
await refreshVehicles()   // AppContext 経由で全画面に反映される
```

注意点:
- **保存先は `Vehicle`(写真テーブルではない)**。数値3つと軽く、`listActive()` に載せても負荷にならない。一方サムネイル一覧は写真の ObjectURL しか持っていないため、Vehicle 側にあると `refreshVehicles()` の既存経路でそのまま全画面に届く
- **`setPhotoAdjust` は `photoUpdatedAt` を変えない**。位置を動かすたびに ObjectURL を作り直して画像を再デコードさせないため。UI 側も調整値を ObjectURL の依存配列に入れないこと
- **写真を差し替え・削除すると調整値は自動で既定値に戻る**(リポジトリが同一トランザクションで処理)。フォームで写真と調整を同時に確定したい場合は `update(id, { photo, photoAdjust })` と一度に渡す(この場合は渡した調整値が優先される)
- 既定値と同じ値を保存すると**キーごと消える**(DB上「調整なし」の表し方を1つに保つため)。読み出しは必ず `normalizePhotoAdjust()` を通すこと
